Introduction

Problem and goal

  • Support teams receive free-text messages that must reach the right queue quickly.
  • Goal: classify each new message into an intent, map it to a team, and send uncertain or out-of-scope messages to a human agent.
  • Constraint: everything runs locally on a CPU-only laptop, so the model in the app must be small and fast.
  • Approach: compare a four-model ladder, from classical NLP to a fine-tuned BERT, then compress BERT by knowledge distillation followed by INT8 quantization.

150 intents in 10 domains + 1 out-of-scope class = 151 labels. Loaded from Hugging Face clinc_oos.

Scope: CLINC150 is a general assistant-intent dataset (banking, travel, small talk, …). It is not an appliance-fault dataset. The product and model-code features are rule-based and were not evaluated.

Regex normalization (src/data.py)

  • Merge model codes before lowercasing: WM-3500 → wm3500
  • Lowercase; shorten repeated letters: loooove → loove
  • Strip punctuation; collapse whitespace
  • The same function is used in training, evaluation and the app

Bug found and fixed in the audit

The original code-merging regex also joined ordinary words to numbers (send 100 → send100) in 646 of 23,850 texts (2.7%). The fixed rule only merges real model-code patterns.

Knowledge distillation (Hinton et al., 2015)

  • Student = teacher config with 4 instead of 12 encoder layers, initialized from the teacher's embeddings, first 4 layers, pooler and classifier
  • Teacher frozen (eval mode, no gradients); its logits are the soft targets
  • Loss = 0.5 · T² · KL(teacher ‖ student) + 0.5 · CE(label), T = 2
  • AdamW lr 3e-5; best validation epoch kept
  • Parameters about halved (2.1×): the 23.4 M-parameter word-embedding table is not reduced

Dynamic INT8 quantization

  • torch.ao.quantization.quantize_dynamic on the student's nn.Linear layers (qint8)
  • Weights stored as int8; activations quantized at run time; CPU engine onednn
  • Saved as state_dict + config; reloading was verified to give identical logits and 26 INT8 layers
  • The app refuses to start if the loaded model is not smaller than the teacher or has no INT8 layers

Conclusion

Conclusions

  • Distillation + INT8 kept almost all of the teacher's accuracy (0.839 vs 0.843) with 3.5× less disk space and 3.8× lower CPU latency, so it is the right model for the CPU app.
  • Quantization cost about 0.8 accuracy points (supplementary FP32 student: 0.847).
  • The FP32 student slightly beat the 2-epoch teacher, most likely because it trained for 3 more epochs. This does not show that distillation beats the teacher in general.
  • TF-IDF + logistic regression is a strong, cheap baseline (0.823 at about 1 ms). Word2Vec + MLP is clearly the weakest model (0.636).
  • All four ladder models were trained and benchmarked locally on CPU with one reproducible script, and the app runs the compressed model end to end.
Main weakness: out-of-scope recall is low for every model (0.26–0.47 across the four ladder models). Even the app model detects only 46% of out-of-scope test messages with plain argmax.

Conclusion

Limitations and future work

Limitations

  • Low OOS recall (0.26–0.47). The benchmark uses plain argmax. The app's confidence threshold adds a human fallback, but its effect was not measured, and it cannot catch confident errors (see "freeze my credit card").
  • The teacher trained for only 2 epochs on CPU; its validation loss was still falling.
  • CLINC150 is not real support-ticket data. The team mapping and product/code rules are hand-written and not evaluated (e.g. "my machines are broken" is rewritten to "my machine are broken" and tagged as a washing machine).
  • Latency varies with background load (TF-IDF: 0.73 ms in the training run vs 1.33 ms in the evaluation run).
  • The embedding table stays FP32; torch.ao.quantization is deprecated (removal planned for PyTorch 2.10).

Future work

  • Tune the OOS threshold on the validation split and report the resulting OOS recall and accuracy.
  • Train the teacher for more epochs, then re-distill.
  • Evaluate on real support tickets; train a dedicated appliance-fault classifier.
  • Quantize the embeddings as well or migrate to torchao; try 2–3-layer students.
